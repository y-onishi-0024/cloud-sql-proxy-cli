# Cloud SQL接続CLI 初期版 実装計画

> 実装担当は `superpowers:executing-plans` を使う。Stageは作業区切りであり、別チャット・別担当を増やす単位ではない。

## 目的・正本・実行方式

Go製 `csql` に、横断検索・対話選択・キャッシュ・Proxy接続・status/stop・doctor/setupを実装する。
正本は [承認済み設計](../specs/2026-10-14-csql-design.md)。本計画はその範囲を実装する。
Goから公式外部コマンドを利用し、インストール・子プロセス・保存・制御通信の境界を重点検証する。

- 作業場所: リポジトリのルートディレクトリ。
- 現在はGit未初期化。base SHAは実装開始時に設計・計画の初期コミットで確定する。
- 実行案: 親が全Stageの実装・検証・修正を所有し、履歴なしの独立Reviewer 1名が全体を監査する。
- 実装は現在のモデル・設定を維持する。複雑な状態・副作用境界を扱うためhigh相当の判断を必要とする。
- Reviewer候補: GPT-6.1 Sol high。起動時にrouting-development-workの現行条件を照合する。
- 現担当・実装subagent・別チャットを比較: 各StageでCLI設定・外部実行・保存形式を共有するため現担当が継続する。Stageごとの引継ぎと統合作業を追加しない。別チャットは明示依頼がなく作成不可。
- 独立Reviewerのみ内部委譲する。実装者から独立した監査が必要なため採用する。並列化・利用量削減を根拠にしない。
- 範囲内の実装→focused検証→独立レビュー→blocking修正→同じReviewerの再確認→最終gateまでを一続きに進める。
- レビュー1回、blocking修正後の再レビュー1回を目安とする。設計変更は親へ戻す。
- push・PR/MR・merge・deploy・実環境での接続／既存Proxy停止は行わない。

| CLI引数 | `github.com/spf13/cobra` v1.10.1 |
| 対話UI | `github.com/charmbracelet/bubbletea` v1.3.10 |
| TTY判定 | `github.com/charmbracelet/x/term` v0.2.1 |

| 検索 | 最大4並列、各コマンド60秒、プロジェクト一覧も60秒 |
| 診断 | 各バージョン確認10秒、ローカル認証一覧10秒 |

| 終了 | 通常停止後10秒で所有子プロセスを強制終了 |
| ダウンロード | 各配布物5分、最大256 MiB、HTTPS、最大3リダイレクト |
| 展開 | 合計1 GiB、単一ファイル256 MiB、最大100,000エントリー |
| 制御ID/トークン | crypto/randによる16/32バイト、hex表現 |

開発用Goは公式 `go1.26.9.darwin-arm64.tar.gz` を取得し、SHA-256 `f9bb7c0a02506c5d9bf0d1eb1f7ee6c7684f844ae49558308a0427b830e022cc` と照合して `.tools/` に展開する。
`.tools/`、`.cache/`、`dist/` をGit除外し、`GOCACHE` / `GOMODCACHE` は作業フォルダ内 `.cache/` に指定する。
この導入は開発用であり、製品のsetupとは別。システム全体のGo・mise設定を変更しない。
利用者にGoのインストールを要求しない。Go以外のパッケージ管理は導入しない。

## ファイル構成と契約

単一のGoパッケージ `main` とし、主要フローは `cli.go` → `discovery.go` → `sessions.go` で追える形にする。
外部プロセス、インストール、対話UIは独立検証の価値があるため分ける。小さなhelper専用ファイルは作らない。

| ファイル | 責務 |
| --- | --- |
| `main.go`, `cli.go` | 終了コード、Cobraコマンド、IO・依存注入、接続の主フロー |
| `dependencies.go` | 実行ファイル解決、doctor、gcloudの実行方式、共通の外部実行 |
| `setup.go` | 配布物一覧、導入案内、確認、取得・展開・排他・配置 |
| `discovery.go` | gcloud JSON取得、並列検索、警告、キャッシュ、候補選別 |
| `selection.go` | Bubble Tea選択、部分一致絞込み、取消、非TTY処理 |
| `sessions.go` | ポート選択、Proxy所有、認証付き制御、管理記録、status/stop |
| `process_unix.go`, `process_windows.go` | OS固有の終了通知・子プロセス起動設定のみ |
| `cli_test.go`, `setup_test.go`, `discovery_test.go`, `sessions_test.go` | 外部契約・観測可能な状態遷移の検証 |
| `go.mod`, `go.sum`, `.gitignore`, `README.md` | ビルド、固定依存、日本語の利用手順 |

共通の型・入口は利用するファイルに置く。

- `Instance {Project, Name, Region, ConnectionName, DatabaseVersion string}`、`DiscoveryResult {Instances []Instance; Failures []ProjectFailure}` は `discovery.go`。
- `Executable {Path string; PrefixArgs []string}`、`CommandRunner.Run(context.Context, Executable, []string) ([]byte, error)` は `dependencies.go`。エラーはstderrの原文を保持する。
- `Paths {ConfigDir, CacheDir, ToolsDir string}`、`App` は `cli.go`。本番はOS標準のユーザー領域、テストは一時領域を注入する。
- `App.Run(context.Context, []string) int` をCLI試験の入口とする。入力・出力・TTY判定・runner・制限時間を注入可能にする。
- `App.Discover(context.Context, string, bool) (DiscoveryResult, error)`、`MatchInstances([]Instance, string) []Instance` は `discovery.go`。
- `App.SelectInstance(context.Context, []Instance) (Instance, error)` は `selection.go`。取消を専用エラーとして識別する。
- `ConnectOptions {Port int; PrivateIP bool}` と `App.Connect(context.Context, Instance, ConnectOptions) error`、`App.Status(context.Context) ([]SessionStatus, error)`、`App.Stop(context.Context, string, bool) error` は `sessions.go`。
- `SessionStatus {ID, Project, Name, Region, DatabaseVersion, State string; Port int}`。Stateはrunning/unresponsive/stoppedとし、表示は日本語へ変換する。
- `App.Diagnose(context.Context) Diagnosis`、`App.Setup(context.Context, bool) error` はそれぞれ `dependencies.go` / `setup.go`。DiagnosisはOS/CPUとコマンド別のPath/Version/State、認証準備のStateを保持し、秘密値を含めない。

## 守る外部・保存契約

- 引数はCobraで解釈し、位置引数の後の `-p` も有効。未知フラグ・余分な位置引数・予約コマンドを誤接続へ流さない。
- `help` は成功、入力不備は2、通常失敗は1、利用者のCtrl+Cは130。正常なstop要求による接続コマンド終了は0。
- 既存PATH上の対応コマンドを優先し、非対応／不足なら管理領域の検証済み版へフォールバックする。
- Unixは実行ファイルを直接起動。Windowsのgcloudが `.cmd` の場合はSDKの `lib/gcloud.py` と同梱／対応Pythonを解決して引数配列で起動し、`cmd /c` や入力文字列のシェル評価を行わない。
- gcloud管理版のWindows/Linux amd64は同梱Pythonを使用。他は既存Python 3.10〜3.15を確認し、不足ならgcloud導入を停止して案内する。
- gcloud検索は `--quiet`、JSON、明示 `--project` を利用する。環境を継承するが、プロジェクト・アカウント設定を変更しない。
- 一覧の並びはProject→Name→ConnectionName。警告はstderr、一覧はstdout。
- API結果のConnectionNameを検証し、Project/Nameとの対応と3要素形式を確認する。オプション風の値やクエリ付きの値をProxyへ渡さない。
- キャッシュ識別は承認済み設計の認証・検索範囲をSHA-256で表現する。設定全体や認証ファイル本文を保存しない。
- カスタム認証／APIエンドポイント設定の検出は設定・環境名から行い、該当時はキャッシュを無効化する。
- JSON管理ファイルはユーザー専用領域で作成し、Unixではディレクトリ0700、ファイル0600。シンボリックリンク先への書込みを拒否する。
- キャッシュは一時ファイルからの置換。セッションはランダムID別のファイル。管理インストールは版別ディレクトリへ配置する。
- 管理版の選択記録は実行確認成功後に確定する。失敗した版をCLIが参照しない。
- 標準ポートから最大20増分で空きを検索し、65535を超えない。明示ポート占有時は変更せず失敗する。
- HTTP制御先は管理記録のポートから `127.0.0.1` に組み立てる。任意URLは保存・参照しない。clientは環境のHTTP proxyとリダイレクトを利用しない。
- `/v1/sessions/ID` はGET status、POST stop。2026-10-15承認の補正として、プロトコル版2、nonce付き要求・応答のHMAC-SHA256をconstant-time比較し、ID・接続情報も照合する。共有秘密そのものは送らず、要求と応答で署名対象の識別文字列を分ける。別Origin・不正methodを拒否する。旧版は通信せずCtrl+Cで停止・再起動を案内する。
- stopの応答は所有子プロセスの終了待ち後に返す。重複stopは同じ終了結果を共有し、二重終了・二重削除を防ぐ。
- UnixのProxyはSIGTERMで停止。Windowsは専用プロセスグループへCTRL_BREAKで停止を試み、利用不能なら所有子プロセスを強制終了する。PIDを記録から読み取って停止しない。
- Proxyは一度だけWaitし、異常終了・取消・stopの原因を区別する。制御サーバーと管理記録を終了時に片付ける。

## Stage 1: CLI・診断・確認付き導入

対象: `main.go`, `cli.go`, `dependencies.go`, `setup.go`, `cli_test.go`, `setup_test.go`, ビルド設定、README。
依存: なし。Git初期化・Go導入・依存固定をこのStageに含める。

- [ ] `git init -b main` 後、設計・計画を初期コミットにしてbase SHAを記録する。既存ファイルを削除しない。
- [ ] 固定Goを検証して導入し、Cobra/Bubble Tea/TTY判定の固定版をgo.mod/go.sumへ記録する。
- [ ] 実際に壊れ得る振る舞いを先に試験する: 両方不足、Proxyだけ不足のlist、予約語、位置引数後のフラグ、未認証・非対応版・診断の時間切れ。
- [ ] CLIとdoctor/setupの入口を実装する。version/help/status/stopは外部コマンド未導入でも使える。
- [ ] 確認・取消・非TTYの試験を追加し、確認前に取得・書込みが始まらないことを確かめる。
- [ ] 偽配布物でSHA不一致、不正パス、容量超過、必要Python不足、起動確認失敗、排他、片方だけ成功した場合を試験して実装する。
- [ ] 固定版・公式HTTPSの配布物だけを許可する。redirect先は同じ公式配布ホストのみ。テストのHTTP配布先は依存注入し、製品のフラグでは変更できない。
- [ ] tar/zipの絶対パス、親逸脱、Windowsドライブ／UNC、特殊ファイルを拒否する。リンクは展開ルート内の相対ターゲットだけを許可し、後続ファイルがリンクを経由して外部へ書き込めないようにする。
- [ ] 排他は管理領域での原子的なロックディレクトリ作成。取得不能は説明して終了し、既存ロックを自動で奪わない。
- [ ] 展開完了→起動確認→管理版の確定の順に処理し、通信取消時は自身の一時領域とロックを解放する。
- [ ] focused: `go test ./... -run 'TestCLI|TestDoctor|TestSetup'`。実SDKのインストール・ログインは試験で行わない。

完了条件: 診断・導入案内・確認付き導入を偽外部コマンド／配布物で検証でき、未導入でも利用可能なコマンドを妨げない。
TDD対象: 未導入の案内、確認前の副作用防止、展開・保存境界。設定ファイルだけのREDやprivate helper試験は不要。

- [ ] 部分失敗・全失敗・不正JSON・60秒上限・取消での子プロセス終了を試験する。
- [ ] API必須フィールドとConnectionNameを検証し、候補の表示順・警告先を固定する。
- [ ] アカウント／設定／偽装／検索範囲別キャッシュ、10分期限、破損、書込み失敗、refresh、0件時1回更新を試験して実装する。
- [ ] Bubble Teaで絞込み・上下移動・Enter・Esc/Ctrl+Cを実装する。通常の一覧表示にはTTYを要求しない。
- [ ] focused: `go test ./... -run 'TestDiscovery|TestCache|TestMatch|TestSelection|TestCLI'`。

完了条件: 検索対象の設定を変更せず、候補・検索失敗・キャッシュ利用の結果を正しく返し、誤った候補を暗黙選択しない。
TDD対象: 重複・部分失敗・キャッシュ認証境界。対話UIは入力イベントと最終選択を確認し、装飾文字列を固定するsnapshotは作らない。

## Stage 3: Proxy所有・status/stop

対象: `sessions.go`, `process_unix.go`, `process_windows.go`, `sessions_test.go`, `cli.go`, README。
依存: Stage 1のPathsと解決済みProxy、Stage 2の選択済みInstance。

- [ ] 既定ポート、明示ポート、占有、未知DB、Private IP、Proxy起動失敗の観測可能な契約を試験する。
- [ ] 偽ProxyをGoテスト実行ファイルの子プロセスとして動かし、実際のargv・ログ・終了待ちを検証する。
- [ ] 接続フローで制御listenerを確保し、Proxy起動成功後に管理記録を公開する。公開失敗時はProxyを止める。
- [ ] 認証付きstatus、指定stop、一括stop、二重stop、認証不一致、ID不一致、応答なし、子の異常終了、強制終了期限を試験して実装する。
- [ ] 承認済み認証補正の回帰として、偽制御先の応答反射、要求署名の反射、別nonceの応答再利用、接続情報不一致、旧形式の非通信と案内を検証する。
- [ ] 親取消でも所有子と管理記録が残らず、別の未管理子プロセスが停止しないことを試験する。
- [ ] 制御応答とサーバー終了の順序を確認し、stop側が受付だけで成功と判定しないようにする。
- [ ] focused: `go test -race ./... -run 'TestSession|TestConnect|TestStop|TestPort'`。

完了条件: 複数セッションを別プロセスから確認・停止し、稼働とDBログイン成功を混同せず、所有していないProxyを停止しない。
TDD対象: 制御認証、停止完了、二重stop、取消・強制終了、公開失敗後の回収。

## Stage 4: 統合検証・独立レビュー・最終gate

対象: 全差分、README、必要なblocking修正のみ。

- [ ] READMEに導入、未導入時のsetup、認証の区別、代表コマンド、status/stop、Private IP、部分検索失敗を日本語で記載する。コードの重要境界にも日本語コメントを残す。
- [ ] 偽gcloud→選択→偽Proxy→別CLIのstatus/stopまでCLI境界で統合検証する。実DBへ接続しない。
- [ ] 擬似TTYで上下・絞込み・選択・取消を実際に操作し、端末状態が戻ることを確認する。
- [ ] `gofmt -l` が空、`go vet ./...`、`go test -race ./...`、macOSビルドが成功する。
- [ ] `CGO_ENABLED=0` でdarwin amd64/arm64、linux amd64/arm64、windows amd64をビルドする。Windows/Linux実行確認とは区別する。
- [ ] 実装をローカル候補コミットへ固定し、base/candidate SHA・clean状態・検証argv・Go版・対象差分をReviewerへ渡す。
- [ ] Reviewerは実装者と別担当、read-onlyで全差分を監査する。機能契約、認証・機密、保存境界、外部副作用、重要なテスト不足を対象とする。
- [ ] BLOCKER/HIGHは同じ実装担当がまとめて修正し、同じReviewerで最新candidateを再確認する。MEDIUMは実害と残件を明示し、好みのrefactorは行わない。
- [ ] 同じcandidate・argv・toolchain・環境で成功したgateは再利用する。変更によって無効になったgateのみ再実行する。
- [ ] 最終結果は変更点・検証・未確認項目を日本語で報告し、remote操作は行わない。

完了条件: 独立レビュー済みの候補とgate候補が一致し、ローカルcleanで、実GCP・実DB・Windows/Linux実行の未確認範囲が明示されている。
コミットは初期docsと実装候補の2つを基本とし、blocking修正時のみ必要な追加コミットを作る。

## レビューで重点確認する条件

1. PATHにはv1しかない／gcloudのPythonが起動不能: doctorと管理版への案内をStage 1で検証。
2. 同じ名称の別project／キャッシュが部分失敗を含む: 誤接続と検索成功の誤認をStage 2で検証。
3. セッション記録が古い／制御ポートが別サービスへ再利用: IDとトークン照合・環境proxy無効をStage 3で検証。
4. stopとCtrl+Cと子の終了が同時: Wait・停止・管理削除の一度だけの完了をStage 3のrace試験で検証。
5. setupの部分成功／取消／同時起動: 成功版再利用、未検証版参照禁止、排他解放をStage 1で検証。
