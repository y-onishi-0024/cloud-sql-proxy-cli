# csql内からの更新

状態: 設計案。利用者確認待ち。製品コード・配布・端末は未変更。
基準: main/v0.6.0 `22da84ca766f5cceb302343de103f13e9050628c`。既存checkoutを継続する。

## 目的と合意事項

利用者は、更新のたびにインストーラーをダウンロードし直す操作をなくし、csql内から更新したい。
接続中の画面から更新する場合は「確認後、この画面の接続を停止して更新・再起動する」と利用者が選択した。
取得・検証完了前は接続を止めず、別端末所有のProxyは停止しない。更新後は一覧へ戻り、自動でDBへ再接続しない。
既存プロファイル・ポート・認証・Google依存・PATH設定を保持する。対象はcsql本体だけ。

## 方式の比較と選択

| 方式 | 判断 |
| --- | --- |
| 公式ReleaseへOS/CPU別CLI本体を追加し、csqlが取得・照合・配置 | 推奨。GUIセットアップや展開処理を経由せず、小さい配布物で更新できる |
| 現行installer ZIPを取得して埋込みCLIを取り出す | 実行ファイル内部からのpayload抽出が配布形式へ依存し、更新処理も大きくなるため採用しない |
| Homebrew等の外部パッケージ管理へ委ねる | 管理版ユーザーの画面内更新を満たさず、現行の配布契約も変わるため今回の対象外 |

## 操作と画面

- `csql update`を追加する。最新版を明示取得し、現在版→更新版・配布元・配置先を表示して実行前に確認する。最新版なら変更しない。
- 非対話では適用しない。自動適用のフラグ・ダウングレード・任意版指定・外部URL指定は初版に含めない。
- 通常の接続UIのCtrl+K操作メニューに「csqlを更新」を加える。選択行の有無に依存しない共通操作とし、行の検索やフォーム入力へ混ぜない。profile addには追加しない。
- 起動時の通知は現行の非同期・最大2秒・24時間キャッシュを維持し、新版通知とF1から画面内更新への操作を案内する。起動しただけで取得・適用しない。
- 明示的な更新操作ではキャッシュの古い版を適用せず、公式APIから最新の正式版を再確認する。`CSQL_NO_UPDATE_CHECK`は従来どおり起動時の自動確認を無効にし、利用者が明示したupdate操作は可能とする。
- 確認画面には、版・配布元・実際の配置先・停止する自画面の接続件数・更新後に再接続が必要なことを表示する。既定は取消とする。
- 「確認→取得中→検証中→自画面接続の停止→配置→起動確認→再起動」と進める。通信・容量・ハッシュ・起動検証の準備段階で失敗した場合は接続を維持して元の画面へ戻る。
- 取得・検証中は背景接続の進捗を配送し、重複した更新開始を抑止する。Escは準備を取り消して元の検索・選択へ戻る。Ctrl+Cは従来どおり自画面の接続を停止して終了する。
- 既存の保存・出力・Port変更などの処理中には更新操作を開始させない。更新確認以降も新しい接続・フォーム・行操作を開始させず、表示と既存接続の維持を優先する。
- 通常の終了待機と同じ経路で自画面のworker/Proxy終了を待ってから代替画面を復元する。更新専用の終了理由を通常取消と区別する。停止完了前に置換・再起動しない。
- 停止開始後の失敗では「この画面の接続は停止済み」と明示し、旧版で一覧を開き直すか終了を選べるようにする。勝手に接続を復元しない。
- UI更新成功時は新版の通常起動へ引き継ぎ、古い位置引数・`--profile`・検索条件を再実行しない。`csql update`成功時は新版番号を表示してコマンドを終了する。

## 公式配布と検証

- v0.7.0を最初の搭載版とする案。将来の正式Releaseへinstaller ZIP3種に加え、以下の通常CLI5種を追加する。
- ファイル名は`csql-<版>-darwin-arm64`、`csql-<版>-darwin-amd64`、`csql-<版>-linux-arm64`、`csql-<版>-linux-amd64`、`csql-<版>-windows-amd64.exe`。版は`0.7.0`のようにvを付けない。
- 既存installerと通常CLIは同じソース候補からビルドし、同梱payloadと公開CLIのバイト一致を配布検証へ加える。SHA256SUMS.txtはZIPと通常CLIを列挙する。日本語案内にもCLI内更新と初回移行を記載する。
- 配布の再現性のため、版別ZIP・通常CLI・SHA256を準備し検査する手順をrepositoryの`scripts/`へ置く。既存のinstallerビルドスクリプトを利用し、過去版配布物を保持する。自動公開CIやGitHub認証情報の配布は追加しない。
- APIは既存の固定した公開repositoryの`releases/latest`。メタデータ取得10秒・256KiB上限、draft/prerelease除外、正式な3要素版番号・現在より新しい版・OS/CPUの完全一致asset・uploaded状態・容量・sha256 digestを検査する。
- API応答に複数の同名asset、digest欠落・不正、未対応OS/CPUがあれば実行せず理由とReleaseへの案内を出す。gcloud等の認証情報・Cookie・利用者情報は送信しない。
- 配布URLは固定repositoryと検証済みの版・asset名から構築する。HTTPSのgithub.comからrelease-assets.githubusercontent.comへの既知の配布リダイレクトだけを有限回許可し、任意ホスト・HTTP・URL認証情報を拒否する。認証ヘッダーとCookieを使わない。
- ダウンロードは最大5分、256MiB上限とAPIサイズの厳密一致、ストリームSHA-256を必須にする。ユーザー取消で停止し、途中ファイルを破棄する。
- SHA-256検証後に通常CLIのMach-O/ELF/PEとCPU・Windows console種別を確認し、上限付きの`version`起動で期待する版と一致することを確かめる。これらが成功するまで配置しない。
- 現行setup.downloadはGoogle配布元専用なので、許可範囲を広げて流用しない。GitHub更新用の境界を別に用意し、第三者ツール導入の信頼範囲を維持する。
- GitHub APIとTLS上の公式asset digestを信頼の根拠とし、独立した公開鍵署名による配布認証は今回追加しない。ハッシュ一致を署名検証済みとは呼ばない。

## 配置・排他・復元

- 対象は公式setupで配置したユーザー管理領域`<ConfigDir>/bin/csql`（Windowsはcsql.exe）だけ。実行中の実体がこの配置先と一致し、通常ファイル・リンクでないこと、binary-install.jsonのハッシュと現在のバイナリが一致することを確認する。
- 手動配置・開発用ビルド・別ディレクトリ・管理記録不一致では書き換えず、理由と公式setupで管理領域へ導入する手順を表示する。システム全体の導入や管理者昇格はしない。
- setupと同じ`.path-lock`で更新の競合を拒否する。ダウンロード前に現在状態を捕捉し、最終適用前にロックを取得して現在のバイナリ・receipt・経路が変わっていないか再検査する。ロック待ちで接続を止めない。
- stagingとバックアップは管理領域のbin直下の推測不能な専用ディレクトリに作る。固定ファイル名への上書き、任意パスへの適用、リンク追従を避ける。作業領域とコマンド例には実際の絶対パスを表示する。
- Unixは旧版のバックアップを確保し、同一filesystem上の新版をrenameで置換する。Windowsは旧実行ファイルを専用バックアップ名へrenameしてから、新版を正式名へrenameする。使用中ファイルへの直接書込みはしない。
- Windowsの共有制約等でrenameに失敗した場合、別プロセスを強制終了しない。旧版が正式名に残っていれば変更なしとして終了し、退避後の失敗なら戻す。別端末の接続には触れず、他のcsqlを終了して再実行する案内を出す。
- 配置後に正式パスから`version`を上限付きで確認し、成功時だけbinary-install.jsonを新ハッシュへ更新する。ロックはreceipt確定または復元後に解放し、新版UIの終了待機中は保持しない。receipt確定前の失敗ではバイナリとreceiptを元の組に復元する。
- 復元自体が失敗した場合、成功と報告せず旧版/新版/receiptの残存場所と公式setupによる具体的な復旧手順を表示する。強制終了や電源断での完全な原子性は保証せず、最後の旧版を保持する。
- バックアップは直近の1版と更新状態の記録を保持する。旧プロセスが使用中で削除不能な旧版は後の更新で再整理でき、無関係なファイルを走査・削除しない。残骸を所有物と確認できない場合は削除しない。
- 新版のUIへ引き継ぐ際は端末入出力を渡し、旧UIは再描画・入力読取りをしない。Unixはプロセス置換、Windowsは新版プロセスへ入出力を渡して終了を待つ方式とし、別のコンソールを開かない。起動できない場合は適用完了と再起動失敗を区別する。
- 更新キャッシュに古い通知を残しても新版の比較で自分自身への更新を案内しない。更新がない場合にバックアップ・設定・receiptを変更しない。

## 実装範囲と工程

親がこの設計と実装計画を作成し、承認後は密接に連動する更新・配置・UI状態を同じ担当で直列実装する。独立Reviewer1名が全差分を監査する。別Taskは作成しない。
主要フローはupdates/新しいselfupdate処理/selectionへ集約し、OS専用処理だけをbuild tagで分ける。private helper単位のファイルや新規フレームワーク・依存を増やさない。
実装・レビュー・最終検証を対象とし、この機能のpush/PR/merge/正式公開/端末更新は後続の明示承認で進める。
v0.6.0にはこの機能がないため、最初の搭載版への移行は従来のセットアップが必要。この端末の初回移行は別途依頼に従って行い、未搭載版でも自己更新できるとは案内しない。

## 受入と検証

- 偽Release API/配布物で、新版/同版/旧版、未対応OS・欠落/重複asset・digest・サイズ・HTTP・リダイレクト・取消を検証し、不正なファイルを配置/起動しないことを確認する。
- 一時管理領域と偽CLIで、管理外拒否、receipt不一致、setupと同時更新、通信中の配置変更、置換/起動/receipt失敗と復元を検証する。既存のprofiles/PATH/ツールを変えないことを観測する。
- UI実キーで共通更新操作・選択0件・確認取消・二重開始・背景結果・ダウンロード失敗時の接続維持・所有接続だけの終了・worker待機・端末復元・新版一覧への引継ぎを検証する。接続中の更新を拒否する実装で代替しない。
- 更新する親が入力を読まず子へ引き継ぐ境界、Ctrl+Cと取得取消、古い更新結果による画面上書き、Windowsの退避失敗/他プロセス使用中を再現可能な境界テストで保護する。
- 全体race、installer race、両vet、gofmt/diff、CLI5環境/installer3環境ビルド、公開予定raw CLIとinstaller payload一致、3テーマの実PTYを同一候補で確認する。実クリップボード・実GCP・稼働中ユーザー接続は使わない。
- macOS実機の一時管理領域で置換と再起動を確認する。Windows実機がなければcross-buildや偽OS境界だけで完了を装わず、実機未確認を残す。
