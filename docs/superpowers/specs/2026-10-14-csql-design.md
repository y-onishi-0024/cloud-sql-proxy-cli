# Cloud SQL接続CLI 初期版設計案

状態: 2026-10-14にユーザー承認済み。次に実装計画を確認する。
制御認証は独立レビューを受けた補正を2026-10-15にユーザー承認済み。以下に補正後の契約を反映する。

## 目的と確認済みの要望

インスタンス名は分かるのにプロジェクトとリージョンを調べ直す手間を減らす。
`csql sample` のような短いコマンドから、アクセス可能なプロジェクトのCloud SQLを検索し、公式Cloud SQL Auth Proxyを起動できるようにする。

参照元は「Cloud SQL接続CLI案」の会話。2026-10-14の本チャットで、Goを採用し、初期版に `status` / `stop` を含める希望を確認した。
検索・選択・キャッシュ・Proxy起動を含める。履歴・お気に入りは後続とする。
外部コマンドが未インストールの場合の診断・導入支援も初期版に含める。
同日の追加確認で、診断・導入手順の表示・実行前確認付きインストールを含めることを確認した。

## 採用する構成

Go製CLIからインストール済みの `gcloud` と `cloud-sql-proxy` v2を呼び出す。
CLI本体は単一実行ファイルとしてビルドするが、利用時にはこの2つの外部コマンドも必要になる。

候補の比較:

| 構成 | 利点 | 負担 |
| --- | --- | --- |
| Go + 外部コマンド（採用案） | 既存の認証・公式Proxyを利用でき、CLIを各OSへ配布できる | 外部コマンドの導入が必要 |
| Go + Google Cloud SDK | 外部 `gcloud` を不要にできる | 認証、ページング、APIエラーの実装・保守が増える |
| Shell + fzf | 検索・接続を小さく作れる | OSごとの差とセッション管理の保守が大きい |

macOS・Linux・Windowsを対象とする。初期開発環境はmacOS。
外部プロセス、保存、制御通信を境界として分けるが、小さなhelperごとにファイルを増やさない。
対話選択にはGo用の既存ライブラリを利用し、ライブラリとGoの版は実装計画で固定する。

## コマンド契約

| コマンド | 動作 |
| --- | --- |
| `csql` | インスタンス一覧を対話選択して接続 |
| `csql NAME` | 名前で検索して接続 |
| `csql connect NAME` | 明示的な接続サブコマンド。NAME省略時は一覧選択 |
| `csql list [QUERY]` | 一覧または絞り込み結果を表示。Proxyは起動しない |
| `csql status` | このCLIが管理するセッションを表示 |
| `csql stop SESSION_ID` | 指定した管理セッションを停止 |
| `csql stop --all` | このCLIが管理するセッションをすべて停止 |
| `csql doctor` | 外部コマンド・バージョン・認証の準備状況を診断 |
| `csql setup` | 不足している外部コマンドのOS別導入手順と認証手順を案内 |
| `csql setup --install` | 導入内容を表示し、対話確認後に不足コマンドをインストール |

接続・一覧の共通オプションは `--project PROJECT_ID` と `--refresh`。
接続オプションは `-p` / `--port PORT` と `--private-ip`。
`--project` 指定時はプロジェクト一覧の取得を省略し、指定プロジェクトのみ検索する。
`status` / `stop` はGCP APIへの問い合わせやログインを必要としない。
引数なしの `stop` は停止せず、対象指定の使い方を表示する。
予約されたサブコマンドと同名のインスタンスには `csql connect NAME` を使う。

検索はインスタンス名の完全一致を優先し、完全一致がなければ名前の部分一致を使う。大文字・小文字は区別しない。
同名インスタンスが複数プロジェクトにある場合は自動決定せず、プロジェクト・リージョン・DB種別を表示して選択する。
候補が複数、またはNAME省略時は対話選択する。非対話環境で選択が必要なら候補を表示してエラー終了する。
0件はエラーとし、検索できなかったプロジェクトがあれば「存在しない」と断定しない。
選択画面では絞り込み、上下移動、Enterで選択、Esc / Ctrl+Cで取消を可能にする。
ヘルプとCLI固有のメッセージは日本語。公式コマンドのエラーとログは原文を保持する。

## 未インストール時の診断・導入支援

接続コマンドは検索前に `gcloud` と `cloud-sql-proxy` を確認する。
利用可能なPATH上の既存コマンドを優先し、見つからない／非対応の場合はCLIが導入した管理領域を確認する。
使う実行ファイルのパスと版を診断で表示する。既存の対応済みインストールを更新・上書きしない。
`list` は `gcloud` のみを必須とし、Proxy未導入でも一覧を取得できる。
`status` / `stop` / ヘルプ / `setup` は外部コマンド未導入でも実行できる。
不足時は不足コマンド名と `csql setup` の案内を表示して非0で終了する。
通常の接続・一覧・診断が暗黙にインストールを開始することはない。

`doctor` は次を個別に表示し、一部の失敗があっても残りの項目を診断する。

- OS・CPUアーキテクチャ。
- PATH上とCLI管理領域の実行ファイルの有無、実際に利用するパス、バージョン。
- 実行ファイルが見つかるが起動できない状態と、未導入・PATH未設定の可能性。
- Proxy v1など初期版の対象外のバージョン。
- gcloudのアクティブアカウントの有無とADCの準備状況。

バージョン確認には各コマンドの `--version` を使い、10秒で打ち切る。
gcloudアカウントの確認はローカルの認証一覧を参照する。
ADCは環境変数と標準の認証ファイルの存在から準備状況を確認するが、認証ファイル本文・秘密鍵・トークンは読み出し・表示しない。
実際の認証有効性・IAM権限・ネットワーク疎通は検証しないため、その状態は「未検証」と表示する。
認証の種類を安全に判断できない場合は「要確認」とし、未ログインと断定しない。
不足や非対応を検出した場合は非0、ローカルの準備確認が完了した場合は0とする。

`setup` は診断結果を使い、macOS・Linux・Windowsに合わせた導入手順と公式配布元を表示する。
macOSはHomebrewが導入済みなら `brew install --cask gcloud-cli` と `brew install cloud-sql-proxy` を案内し、Homebrewがなければ公式配布物の導入手順を案内する。
Linuxは公式gcloudのOS別パッケージ／アーカイブ手順、Windowsは公式gcloudインストーラーを案内する。
Proxyの公式配布物はOS・CPUに対応するものを案内し、非対応の組合せでは別アーキテクチャの実行ファイルを案内しない。
配布物の版・URL・検証方法は実装計画で固定する。`latest` の無条件ダウンロードは行わない。
導入後は `csql doctor` で再確認し、PATHに反映されていなければ設定方法とターミナル再起動を案内する。
インストール失敗、権限不足、通信失敗は成功扱いにしない。

`setup --install` はOS・CPU、不足／非対応のコマンド、導入する版、公式配布URL、保存先、実行する操作をまとめて表示し、対話で確認を得てから実行する。
非対話環境では案内を表示して終了し、暗黙の承認は行わない。初期版に確認を省略するオプションは設けない。
初期版の自動導入はユーザー専用のCLI管理領域へ行い、システム全体のパッケージ管理・管理者権限を必要としない。
Homebrewなどの既存パッケージ管理による導入は手動選択肢として案内する。

gcloudはGoogle公式の版付きアーカイブを展開し、ProxyはGoogle公式の版付き実行ファイルを配置する。
自動導入の対象はmacOS amd64/arm64、Linux amd64/arm64、Windows amd64とし、公式配布物を確認できない組合せは手動導入を案内する。
WindowsとLinux amd64のgcloudは、固定する版に同梱Pythonがある配布物を優先する。
同梱Pythonのない配布物では既存の対応Pythonが必要であり、不足時はPythonの導入手順を示して該当導入を停止する。Python自体の自動導入は行わない。

配布物は公式HTTPS URLから一時領域に取得し、実装計画で固定したSHA-256と照合してから配置する。
チェックサム不一致、通信失敗、対応版不明の場合は実行・配置しない。
展開先から逸脱するパスとリンクを拒否し、ダウンロード時間・容量と展開後容量の上限を設ける。値は実装計画で固定する。
同時インストールは管理領域で排他し、検証済みの一時領域を確定して途中の配布物を利用させない。
インストール後は配置したコマンドの起動と版を確認し、その結果を対象ごとに表示する。
片方のみ導入できた場合は部分完了と不足を表示して非0で終了し、成功した導入は次回再利用する。

管理領域のコマンドはCLIから直接参照できるため、通常操作ではシェル設定やグローバルPATHを書き換えない。明示的な `setup --path` による確認付きユーザーPATH設定は、後続の[PATH設定仕様](2026-10-15-path-support-design.md)に従う。
利用者が単独でgcloudを使う場合のPATH設定と、管理領域の実行ファイルを直接指定したログインコマンドを表示する。
認証初期化・使用状況送信の有効化・GCPプロジェクト設定はインストール操作に含めない。

未認証の場合は `gcloud auth login` と `gcloud auth application-default login` を別々の目的として案内する。
初期版ではログインコマンドを自動実行せず、利用者がアカウントを選択して実行する。
導入支援のために現在のGCPプロジェクトを設定・変更することはない。

## 検索と認証

`gcloud projects list --format=json` で列挙できたプロジェクトを対象とし、各プロジェクトで `gcloud sql instances list --project=... --format=json --quiet` を実行する。
全GCPプロジェクトへのアクセスを保証するものではなく、現在の認証で列挙・参照できる範囲を検索する。
並列数は4に制限し、各問い合わせには60秒の上限を設ける。取消時は未完了の問い合わせも終了する。
プロジェクトごとの権限不足・API無効・通信失敗は個別に表示し、成功した結果は利用可能とする。
すべての問い合わせが失敗した場合は検索失敗として終了する。APIの有効化は行わない。

検索には現在の `gcloud` 設定を使い、`gcloud config set project` やログインの変更は行わない。
Proxyは標準のApplication Default Credentials（ADC）を使う。
`gcloud auth login` とADCのログインは別であることをREADMEに記載する。
検索できてもProxyの認証・権限により接続できない場合は、Proxyのエラーを表示する。
CLIはトークン・DBパスワード・サービスアカウント鍵を取得・保存しない。

## キャッシュ

一覧と取得時刻、検索範囲、検索失敗プロジェクトをJSONで保存し、有効期限は10分とする。
`--refresh` は期限にかかわらず更新する。通常接続で検索結果が0件の場合は1回だけ更新して再検索する。
gcloud設定ディレクトリ、アクティブ設定名、実効アカウント、偽装サービスアカウント、検索対象プロジェクトの組合せをキャッシュ識別に使う。
独自のAPIエンドポイントや認証ファイルなど、初期版で安全に識別できない認証設定ではキャッシュを使わない。
別アカウント・別検索範囲のキャッシュを混用しない。
破損・期限切れは再取得する。更新失敗を理由に期限切れの一覧へ暗黙に戻さない。
検索失敗プロジェクトはキャッシュ利用時も表示し、利用者が `--refresh` で再検索できるようにする。
ユーザー別のOS標準キャッシュ領域に保存し、一時ファイルからの置換で途中のJSONを読ませない。
書込み不能時は警告して現在の検索結果で続行する。

## Proxyの起動・終了

選択したAPI結果の `connectionName` をそのまま接続対象とする。利用者入力から接続名を組み立てない。
外部コマンドはシェルを介さず、引数配列として実行する。
待受アドレスは `127.0.0.1` に固定する。
標準ポートはPostgreSQL 5432、MySQL 3306、SQL Server 1433。
未知のDB種別は明示的なポート指定を求める。
明示ポートは1〜65535。使用中の場合はエラーとしてProxyを起動しない。
省略時に標準ポートが使用中なら、以降の20ポートを順に確認し、選んだポートを表示する。
ポート確認とProxy起動の間の競合による起動失敗は、Proxyのエラーとして扱う。

Proxyはフォアグラウンドで動作し、接続コマンドは子プロセスの終了まで待つ。
表示する接続情報はホスト・ポート・プロジェクト・リージョン・インスタンス・DB種別・セッションID。
起動要求、子プロセスの稼働、DBへのログイン成功を区別し、DB接続に成功したとは表示しない。
標準出力・標準エラーへProxyのログを渡し、異常終了時は非0で終了する。
Ctrl+C、終了シグナル、`stop` で、このコマンドが所有する子プロセスを終了して終了待ちする。
停止要求後10秒で終了しない場合は、所有している子プロセスを強制終了する。
Windowsのシグナル制約には専用の小さな処理で対応する。
`--private-ip` はProxyへ渡す。VPN・VPCへのネットワーク経路は別途必要。

## status / stopの管理境界

複数ターミナルで起動したProxyをそれぞれ管理できるようにする。
バックグラウンド常駐化は初期版に含めず、別ターミナルから `status` / `stop` を使う。

接続コマンドは、セッションごとにランダムIDと認証トークンを生成し、ループバックの空きポートに小さな制御HTTPサーバーを起動する。
セッションファイルにはID・接続情報・制御ポート・制御トークン・プロトコル版2を保存する。
保存先はユーザー専用のOS標準設定領域内。Unixではディレクトリ0700、ファイル0600とする。
Windowsではユーザープロファイルの権限を利用する。制御トークンは画面・ログへ表示しない。
CLIのセッション管理用トークンはGCP認証情報とは別である。

`status` は保存された制御先へ認証付きで問い合わせ、セッションID・接続情報も照合する。
制御トークン自体は通信で送らない。各要求の32バイトのランダムnonceと、要求・応答双方のHMAC-SHA256を検証して所有者を確認する。
要求の署名対象は `csql-request-v2`、nonce、method、pathを改行で結合した文字列。
応答の署名対象は `csql-response-v2`、同じnonce、HTTP status、本文のSHA-256を改行で結合した文字列。
署名をconstant-time比較し、署名欠落・反射・別要求の応答再利用を拒否する。
旧版または非対応の管理記録から通信せず「応答なし」とし、起動した端末からCtrl+Cで停止して再起動する手順を表示する。
生存確認できた子プロセスの稼働状態と接続情報を表示する。DBログインの成否は対象外。
制御先へ接続できない記録は「応答なし」と表示し、PIDから稼働中と推定しない。
一覧表示は制御先ごとに2秒の通信上限を設け、最大4並列で処理する。

`stop` は認証付きPOSTで所有者へ停止を要求する。所有者が子プロセスを停止する。
管理ファイルのPIDや任意のOSプロセスへ直接シグナルを送らない。
トークン不一致・ID不一致・応答なしの場合は停止成功と扱わず、プロセスには触れない。
停止要求の受付と停止完了を区別し、子プロセスの終了通知を受けて完了とする。
停止通信は強制終了への移行も待てるよう対象ごとに15秒の上限とし、一括停止は最大4並列で処理する。
一括停止で一部が失敗した場合は対象ごとの結果を表示して非0で終了する。
正常終了時は自身のセッションファイルを削除する。強制終了で残った記録は応答なしとして扱う。

## 受入条件と検証

1. 現在のgcloudプロジェクトを変更せず、異なるプロジェクトのインスタンスを名前で解決できる。
2. 同名候補の誤接続、非対話環境での暗黙選択を防ぐ。
3. 一部検索失敗を隠さず、有効な検索結果とキャッシュを利用できる。
4. 明示ポート、標準ポート、占有時の候補選択、Private IP指定がProxyへ正しく反映される。
5. Proxy起動失敗・取消・終了で、所有する子プロセスと管理ファイルを適切に処理する。
6. 別ターミナルから複数セッションを確認・停止でき、未管理プロセスや認証不一致の制御先を停止しない。
7. macOSでテスト・静的検査・ビルドが成功し、Linux・Windows向けビルドも成功する。
8. 両コマンド未導入・片方のみ導入・Proxy v1・起動不能・バージョン確認の時間切れを区別し、導入手順を表示できる。Proxy未導入でも一覧・管理コマンドの利用を妨げない。
9. 導入案内はOS・CPUに対応し、認証情報を出力せず、通常操作や診断がインストール・ログイン・GCP設定変更を開始しない。
10. インストールは対話確認後だけ実行し、取消・非対話・チェックサム不一致・不正な展開パス・必要Python不足で意図しない導入を行わない。既存の対応コマンドを再利用し、部分失敗と正常導入を区別する。

自動検証は偽のgcloud / Proxyと一時ディレクトリを使う。
重点は検索重複・部分失敗、認証別キャッシュ、実引数、子プロセス終了、制御認証、停止完了、依存コマンド不足時の案内と利用可能コマンドの確認。
導入は偽の配布サーバーと一時領域で、確認・取消、改ざん検出、展開境界、実行確認、既存導入再利用、部分失敗を検証する。
private helperや単純な委譲だけのテストは追加しない。
実GCP検索、実Proxy接続、各OSでの実行確認は自動検証とは分けて結果を報告する。
実GCPや既存Proxyを無断で変更・停止しない。
